# Updater safety and convergence

- Do not run the live update cycle, install packages, register continuation tasks, mutate services, or reboot merely to test a change unless the user explicitly authorized that live-system effect.
- The `Global\BootUpdateCycle` mutex is a fail-closed safety boundary shared by elevated-user and SYSTEM tasks. Preserve its explicit SYSTEM/Administrators ACL.
- Persist checkpoints atomically before mutation and preserve user-versus-SYSTEM scope across every continuation.
- Treat provider exit codes as evidence, not phase outcomes. Winget/MSI `1605` is an already-absent stale uninstall record. Reconcile aggregate `0x8A15002C` only when structured output accounts for every attempted package as verified success, `1605`, or a user-scope package that elevated Winget definitionally cannot replace (scope-blocked). Scope-blocked packages are deferred inventory with logged remediation — never verified updates and never retry fuel.
- Boot-session identity is a tolerance window, never string equality. `Win32_OperatingSystem.LastBootUpTime` is derived and jitters by seconds between same-boot reads on VMs and clock-resyncing hosts; comparing it exactly reads as a fresh boot, silently zeroing `ConsecutiveRetryCount` and invalidating same-boot Windows Update evidence, so the retry limit never fires. Compare through `Test-BootUpdateSameBootSession` and anchor `LastBootSessionId` on the first identity observed for the boot so drift cannot ratchet past the tolerance. The tolerance only holds if the value keeps its type across the state file: `ConvertFrom-Json` rehydrates an ISO-8601 string as `[datetime]`, and rendering that back to text drops the offset, so the comparison silently picks up the machine's whole UTC offset rather than seconds of jitter. Normalize persisted timestamps through `ConvertTo-BootUpdateTimestampString` and never bind one to a `[string]` parameter. Tests that feed string literals to the comparison cannot see this class of defect; assert across a `ConvertTo-Json`/`ConvertFrom-Json` round-trip.
- Resolve `MpCmdRun.exe` through `Get-DefenderCommandPath`, never by hardcoding `$env:ProgramFiles\Windows Defender`. That copy is the OS-inbox stub frozen at the OS build's release version, while the serviced platform under `%ProgramData%\Microsoft\Windows Defender\Platform` advances independently; on Windows Server 2016 the stub stays at 4.10.14393.x and cannot bind an export in a 4.18.x engine. Order platform directories as `[version]`, never as strings.
- Defender `hr=0x8007007F` (`ERROR_PROC_NOT_FOUND`) is a broken or mismatched Defender platform, not a content or network condition: it fails identically on every same-boot invocation. Classify it as a terminal failure with a platform-repair attention detail instead of queueing retries. Ordinary signature-update failures stay retryable.
- A Python interpreter that cannot start (`Fatal Python error`, missing `encodings` module, missing platform-independent libraries) is a permanent same-boot environment failure: classify the Pip phase as a terminal failure requiring manual attention instead of queueing retries, and propagate `TerminalFailure` from parallel-cohort results to the completion disposition.
- Never count `1605`, a provider trigger, or an inferred action as a verified update. Do not queue a retry for a fully reconciled stale record. Preserve the phase-level regression in `tests/RebootResilience.Tests.ps1`.
- Treat a fully accounted Winget/MSI `1605` as independent Windows Installer evidence that the product code is not installed, even when Winget continues to enumerate the stale record. Key learned outcomes by package ID, scope, code, and observed version; invalidate on success or changed failure evidence. Never ask Winget inventory to disprove its own stale inventory, and never suppress recovery choices when durable persistence fails.
- `Windows\SystemTemp\ChocolateyPrototype-2.8.5.130` belongs to Microsoft PackageManagement/OneGet's legacy Chocolatey provider, not the independent `choco.exe` CLI. Treat blank-destination delete markers there as non-blocking housekeeping, retain their sanitized provenance, and never rewrite the shared `PendingFileRenameOperations` value to clean them up.
- Avoid broad `Get-Package`, `Find-Package`, or forced provider-discovery probes in the orchestrator. They can initialize or bootstrap legacy PackageManagement providers and create unrelated system state during an otherwise read-only assessment.
- Completion claims require provider convergence, settled restart evidence, truthful verified counts, and verified cleanup of continuation tasks and state.
