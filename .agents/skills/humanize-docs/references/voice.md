# Boot Update Cycle voice

The user wants documentation that sounds conversational, direct, and somewhat snarky,
while staying useful as a reference. Getting started should not require reading a wall
of text. The user specifically rejected obvious AI patterns and forced "human" jokes.

Keep the useful explanation first. A dry aside can stay when it fits the actual task;
plain prose is better than manufacturing a joke. Technical reference material should
stay precise. Do not make every paragraph equally short or end every section with a
punchline. The BBS artwork and product names are intentional; a prose pass does not
redesign them.

The following were rejected or identified as the same failure:

| Problematic wording | What to do |
|---|---|
| "The repair plan no longer gets to improvise." | Describe the specific repair condition and command. Software does not improvise. |
| "Software becomes folklore." | Explain task cleanup if the reader needs it; remove the slogan. |
| "AWS gets its own side quest because of course it does." | State that AWS tooling is opt-in and give the command. |
| "A clear, reversible explanation." | Name the reversible action if one exists. An explanation is not reversible. |
| "Old versions look lonely." | State the compatibility reason for retaining old modules. |

A suggested factual rewrite of the rejected release opener is:

> Fixes the AWS CLI repair instructions for machines where Winget reports a successful
> update but Chocolatey still fails.

This is an editorial example, not a user-approved writing sample. The conversation
provides preferences and corrections, not enough authored prose to claim an exact
personal voice match. Update this reference when the user supplies further examples
or corrections; do not label the agent's own drafts as the user's voice.
